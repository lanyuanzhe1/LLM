# 知识库文件展示与智能体广场技术方案

> 日期：2026-08-27
> 状态：待实施
> 原则：满足当前展示需求，保持实现简单，不引入不必要的基础设施

## 1. 文档目的

本文档定义两个前端功能的最小可实施方案：

1. 用户登录后可以查看公共技术知识库和当前项目知识库中的文件，点击文件后查看后台实际切分出的知识块。
2. 左侧导航增加“智能体广场”，用户进入广场后可以浏览彩色智能体卡片，并跳转到讯飞发布的对应智能体页面。

本方案复用现有 FastAPI、向量库产物和讯飞智能体分享链接，不建设新的平台级能力。

## 2. 范围

### 2.1 本次实现

- 登录后左侧导航增加“知识库”。
- 展示公共技术知识库文件。
- 展示当前 `project_id` 对应的用户/项目知识文件。
- 点击文件查看该文件的全部知识块。
- 左侧导航增加可展开的“智能体广场”。
- 新增彩色智能体广场页面。
- 点击智能体卡片，在新标签页打开讯飞智能体分享链接。

### 2.2 本次不实现

- 不修改现有文件上传和切块流程。
- 不增加数据库、Redis或后台任务队列。
- 不增加新的用户权限系统，继续沿用现有 `project_id` 机制。
- 不开发智能体管理后台。
- 不通过 API 在本系统内运行讯飞智能体。
- 不使用 iframe 嵌入讯飞页面。
- 不同步讯飞智能体会话历史。
- 不增加自动化测试，只做上线后的人工点击验收。

## 3. 当前基础

当前向量库已经保存了页面展示所需的数据：

```text
vector_store/<当前基础库>/
├── manifest.json
├── chunks_metadata.json
└── vectors.npy

vector_store/projects/<project_id>/
├── manifest.json
├── chunks_metadata.json
└── vectors.npy
```

`manifest.json` 包含：

- 文件相对路径；
- SHA-256；
- 文件大小；
- 处理状态；
- 知识块数量。

`chunks_metadata.json` 包含：

- `source`：来源文件相对路径；
- `text`：知识块正文；
- `start_pos`：知识块在解析文本中的开始位置；
- `char_count`：知识块字符数；
- `document_checksum`：来源文件摘要；
- `scope`：`base` 或 `project`；
- `project_id`：项目知识块所属项目。

因此本次只需要增加读取接口，不需要重新解析、切块或向量化。

## 4. 调研结论与技术决策

### 4.1 这两个需求本质上是什么

本次需求不涉及新的 RAG 算法，也不涉及智能体编排能力建设，本质上是两项传统 Web 开发工作：

1. 把后台已有的文件和知识块元数据通过 HTTP 接口提供给前端，再由前端渲染。
2. 在现有前端增加一个智能体目录页，通过配置好的链接把用户带到已经发布的讯飞智能体。

因此设计重点不是增加新的技术组件，而是找到现有数据、定义最小接口并完成页面路由。

### 4.2 为什么不能只扩展现有 `/v1/sources/{evidence_id}`

现有来源接口的调用方向是：前端已经知道一个 `evidence_id`，再查询这个证据块的详情。新需求的调用方向则相反：

```text
先列出全部文件
    → 用户选择一个文件
    → 再列出这个文件的全部知识块
```

现有接口无法回答“当前有哪些文件”，也无法根据文件查询全部块。强行向该接口增加大量可选参数，会让一个接口同时承担证据详情、文件目录和块列表三种职责。

因此增加两个只读接口更清楚：

```text
GET /v1/knowledge/files
GET /v1/knowledge/files/{document_id}/chunks
```

这是本次唯一必要的后端扩展。

### 4.3 为什么文件列表和知识块分成两个接口

可以让文件列表接口一次返回所有文件和全部知识块，但这样用户只是打开知识库页面，就需要下载整个 `chunks_metadata.json`。当前基础库已有两千多个知识块，这些正文在文件列表阶段并不需要。

分成两个接口后：

- 第一个接口只返回轻量文件摘要，知识库页面打开更快；
- 用户点击某个文件后，第二个接口才返回该文件的知识块；
- 前端状态和错误提示更容易处理；
- 后端仍然只有两个简单的 GET 接口。

这不是复杂化，而是避免传输无用数据的最小拆分。

### 4.4 为什么直接读取现有 JSON 产物

文件目录所需字段已经存在于 `manifest.json`，知识块展示所需字段已经存在于 `chunks_metadata.json`。如果再建立数据库，会产生两份需要同步的数据：

```text
向量库 JSON 产物
数据库文件/块记录
```

一旦入库成功但数据库同步失败，前端看到的数据就可能与模型实际使用的数据不一致。直接读取现有产物具有三个优点：

1. 页面看到的就是当前向量库实际使用的文件和块；
2. 不需要迁移现有数据；
3. 不需要维护额外数据库和同步逻辑。

后端只读取 JSON，不读取向量文件，因为页面不需要 Embedding 向量。

### 4.5 为什么当前不做分页和搜索

当前知识库总块数约两千，单个文件通常只有几十到两百多个块。文件列表本身很小；用户打开一个文件时，一次返回该文件的全部块仍在可接受范围内。

因此当前不实现：

- 游标分页；
- 块搜索；
- 虚拟滚动；
- 服务端索引。

如果以后出现单个文件数千个块，再给知识块接口增加 `offset` 和 `limit` 即可，不影响当前接口结构。

### 4.6 为什么不重做上传流程

用户提出的是“上传后的文件也能看到切分块”，不是重新设计文件上传系统。现有入库流程最终会生成项目级的 `manifest.json` 和 `chunks_metadata.json`，展示接口只需要读取这些结果。

本次边界是：

```text
已有上传/入库流程负责产生知识块
本次新接口负责展示已经产生的知识块
```

如果文件尚未完成入库、尚未出现在 manifest 中，本次页面不展示该文件。这样不需要新增处理状态、任务表、队列和进度轮询。

### 4.7 为什么暂时沿用 `project_id`

当前代码已经以 `project_id` 区分基础知识库和不同项目知识库。完整的生产权限系统通常需要用户、项目和成员关系，但这不是本次展示需求的一部分。

因此当前沿用前端会话中已有的 `project_id`：

- 公共文件来自基础库；
- 用户文件来自 `vector_store/projects/<project_id>`；
- 不额外创建用户—项目数据库。

需要明确：当前 `project_id` 是逻辑隔离，不等于完整的生产级鉴权。如果将来系统面向不互信的公网用户，再单独增加登录身份到项目的授权校验。

### 4.8 为什么智能体广场使用静态配置

讯飞平台负责智能体的创建、编排、调试和发布；本系统只需要展示这些智能体并提供入口。前端真正需要的信息只有：

```text
名称、简介、分类、图标、颜色、分享链接
```

这些信息数量少、变化频率低，使用 `agents.ts` 管理最直接。增加一个智能体就是增加一条配置，不需要数据库、管理后台或同步程序。

只有出现以下实际需求时，才有必要建设智能体管理后台：

- 非开发人员需要频繁上下架智能体；
- 不重新发布前端就要立即修改目录；
- 需要记录点击量、权限或推荐排序；
- 智能体数量增长到难以维护静态文件。

这些均不属于当前需求。

### 4.9 为什么使用分享链接而不是讯飞 API

存在三种智能体接入方式：

| 方式 | 优点 | 问题 | 当前决策 |
|---|---|---|---|
| 分享链接 | 开发量最小，讯飞负责页面和运行 | 会打开讯飞页面 | 采用 |
| iframe | 用户看起来没有离开系统 | 容易受登录、Cookie、跨域和 CSP 限制 | 不采用 |
| 讯飞 API | 可以做统一的自有聊天页面 | 需要聊天 UI、流式协议、会话状态和错误处理 | 暂不采用 |

用户当前要求是“点击后跳转到这个智能体页面”，分享链接与需求完全一致。采用 API 会把简单的导航功能扩大成新的聊天子系统，没有必要。

### 4.10 为什么不深度修改 Open WebUI

已有方案曾考虑使用 Open WebUI 作为通用聊天前端。它适合快速提供聊天、用户和会话能力，但本次需求需要自定义左侧导航、知识库文件/块页面以及智能体广场。

如果深度修改 Open WebUI：

- 需要维护自己的前端 fork；
- 上游升级时要持续合并改动；
- Open WebUI 自带知识库与当前项目向量库是两套数据源；
- 页面看到的块可能不是当前 RAG 实际使用的块；
- 自定义品牌和大规模部署还需要关注其当前许可证要求。

因此本次方案以“在实际产品前端中增加普通页面”为准，不把 Open WebUI 的内部知识库作为本项目数据源。

### 4.11 为什么不安排自动化测试

本次新增的是两个只读接口、两个知识库页面和一个静态智能体目录，没有复杂计算和状态变更。用户已明确要求不增加测试工作，因此方案不安排单元测试、集成测试或端到端测试。

上线后通过人工点击检查以下事实即可：

- 文件存在时能显示；
- 文件不存在时不显示；
- 点击文件能看到真实块；
- 点击智能体能打开正确链接。

### 4.12 已知边界和后续扩展条件

当前方案有意保留以下边界：

1. `project_id` 只提供逻辑隔离；公网多租户上线前再增加授权校验。
2. 当前知识块没有稳定的 PDF 精确页码，因此只展示块序号和字符位置。
3. 尚未完成入库的文件不展示处理进度。
4. 智能体分享链接由开发人员维护。
5. 单个文件知识块一次返回；数据规模明显增长后再分页。

这些边界都不妨碍当前两个需求完成，也不会阻止以后按实际需要扩展。

## 6. 知识库后端设计

### 6.1 文件位置解析

基础库使用 FastAPI 当前配置的 `settings.vector_store_dir`，从而与实际运行时使用同一套向量库。

项目库使用：

```python
projects_root = settings.vector_store_dir.parent / "projects"
project_store_dir = projects_root / project_id
```

示例：

```text
settings.vector_store_dir = vector_store/bailian-base
基础库                   = vector_store/bailian-base
项目库 demo              = vector_store/projects/demo
```

后端只读取 `manifest.json` 和 `chunks_metadata.json`，不读取 `vectors.npy`。

### 6.2 文档标识

前端不直接使用文件路径作为 URL 参数。后端根据作用域、项目、文件相对路径和文件摘要生成稳定的 `document_id`：

```text
base 文档：
sha256("base\n" + source + "\n" + document_checksum)

project 文档：
sha256("project\n" + project_id + "\n" + source + "\n" + document_checksum)
```

接口响应使用 `sha256:<hex>` 格式。这样可以避免中文路径编码和路径穿越问题，也不需要新增数据库保存 ID。

### 6.3 文件列表接口

```http
GET /v1/knowledge/files?project_id=demo
```

行为：

1. 读取基础库 `manifest.json`，生成 `base_files`。
2. 如果请求提供 `project_id`，读取对应项目库 `manifest.json`，生成 `user_files`。
3. 项目库不存在时返回空数组，不影响公共知识库展示。
4. 文件按照显示名称排序。

响应示例：

```json
{
  "base_files": [
    {
      "document_id": "sha256:abc123",
      "name": "粮油储藏基础知识.pdf",
      "source": "新增书本与PPT/粮油储藏基础知识.pdf",
      "size_bytes": 591506,
      "chunk_count": 131,
      "scope": "base"
    }
  ],
  "user_files": [
    {
      "document_id": "sha256:def456",
      "name": "用户上传文件.pdf",
      "source": "用户上传文件.pdf",
      "size_bytes": 320100,
      "chunk_count": 18,
      "scope": "project"
    }
  ]
}
```

### 6.4 文件知识块接口

```http
GET /v1/knowledge/files/{document_id}/chunks?project_id=demo
```

行为：

1. 在基础库和当前项目库的 manifest 中匹配 `document_id`。
2. 未匹配时返回 HTTP 404，错误码为 `DOCUMENT_NOT_FOUND`。
3. 匹配后读取对应 `chunks_metadata.json`。
4. 使用 `source` 筛选该文件的知识块。
5. 按 `start_pos` 升序排列，并生成从 1 开始的 `index`。
6. 一次返回该文件的全部知识块，不做分页。

响应示例：

```json
{
  "document_id": "sha256:abc123",
  "name": "粮油储藏基础知识.pdf",
  "source": "新增书本与PPT/粮油储藏基础知识.pdf",
  "scope": "base",
  "chunk_count": 131,
  "chunks": [
    {
      "index": 1,
      "start_pos": 0,
      "char_count": 595,
      "text": "知识块完整正文……"
    }
  ]
}
```

本次数据规模下，单个文件只有几十到两百多个知识块，一次返回实现最简单。以后出现单文件数千个知识块时再增加分页。

### 6.5 后端文件调整

新增：

```text
app/api/knowledge.py
app/services/knowledge_catalog.py
app/schemas/knowledge.py
```

修改：

```text
app/main.py
```

职责：

- `app/services/knowledge_catalog.py`：读取 manifest、生成文档 ID、筛选知识块。
- `app/schemas/knowledge.py`：定义文件列表和知识块响应模型。
- `app/api/knowledge.py`：提供两个 GET 接口。
- `app/main.py`：挂载知识库路由。

## 7. 知识库前端设计

### 7.1 路由

```text
/knowledge               知识库文件列表
/knowledge/:documentId   文件知识块详情
```

### 7.2 文件列表页面

页面分成两组：

```text
技术知识库
├── 文件名称
├── 文件大小
└── 知识块数量

我的知识文件
├── 文件名称
├── 文件大小
└── 知识块数量
```

交互：

- 页面进入时调用文件列表接口。
- `base_files` 渲染到“技术知识库”。
- `user_files` 渲染到“我的知识文件”。
- 点击文件跳转至 `/knowledge/:documentId`。
- 当前项目没有用户文件时显示“暂无个人知识文件”。
- 接口失败时显示“知识库暂时无法加载”和重新加载按钮。

### 7.3 知识块详情页面

页面顶部显示：

- 文件名；
- 文件来源分类；
- 知识块总数；
- 返回知识库按钮。

知识块按顺序使用折叠卡片展示：

```text
知识块 1    开始位置 0    595 字符
┌──────────────────────────────────────┐
│ 知识块完整正文                       │
└──────────────────────────────────────┘
```

本次不增加块搜索、编辑、删除、重新切分或向量展示。

### 8.3 页面布局

页面包含：

1. 蓝紫色渐变标题区域。
2. 分类筛选：全部、教学、办公、科研、创作。
3. 智能体卡片网格。

每张卡片显示：

- 彩色图标；
- 智能体名称；
- 一句话简介；
- 分类标签；
- “立即使用”按钮。

视觉规则：

- 页面背景使用浅灰蓝；
- 卡片使用白色背景和轻阴影；
- 不同智能体使用配置中的主题色；
- 鼠标悬停时卡片轻微上浮；
- 不增加复杂动画或图片生成。

### 8.4 跳转行为

点击卡片时：

```typescript

```

讯飞智能体必须提前在讯飞平台发布，并将可访问的分享链接填入 `agents.ts`。链接为空时，“立即使用”按钮显示禁用状态。

## 11. 人工验收

本次不安排自动化测试。上线后按以下步骤人工确认：

1. 登录后，左侧能看到“知识库”。
2. 点击“知识库”，能看到公共技术知识文件。
3. 点击任意文件，能看到该文件的真实知识块。
4. 当前 `project_id` 已有知识文件时，能在“我的知识文件”中看到。
5. 左侧能展开“智能体广场”。
6. 进入广场后能看到彩色智能体卡片。
7. 点击 PPT 制作助手或备课助手，能在新标签页打开对应讯飞智能体。

上述七项全部满足，即完成本次需求。
